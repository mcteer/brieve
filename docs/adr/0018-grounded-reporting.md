# ADR-0018: Reports are compiled from records, never composed from memory

- **Status**: Accepted
- **Date**: 2026-04-08
- **Relates to**: [ADR-0009](0009-adlc-stages-and-observability-planes.md), [ADR-0032](0032-delegated-run-versus-local-loop.md), [ADR-0035](0035-audit-as-a-governed-read-path.md)
- **Requirements**: R4, R10

## Context

A run report — what the agent did, what changed, what was denied, what needs attention —
is often the only artifact a human reads. In regulated settings it becomes evidence, cited
in change records and audit responses.

The obvious way to produce one is to ask the model to summarize the run. It is fluent, it
is cheap, and it is exactly wrong. A model summarizing its own execution is reconstructing
from context, and context is lossy: steps drop out, a failed attempt gets described as
successful, a denial is omitted, an approximate number is stated precisely. The failure is
not random noise — summaries are *plausible*, which means nobody catches them by reading.

This is a category error with real consequences. A report that says "applied successfully
to three workspaces" when a fourth silently failed is worse than no report, because it
terminates the investigation that would have found the problem. Every governance guarantee
upstream — hooks, scoping, audit — is undermined if the artifact humans actually read is
generated by the least reliable component in the system.

## Decision

**Reports are compiled from run records with bounded reconciliation, never composed from
memory.**

- **Typed RunReports** are structured objects populated from the run record — the audit
  entries, hook decisions, tool results, and product run outcomes actually captured.
- **Every claim is validated against the record** before the report is emitted.
  Reconciliation is bounded: a claim that cannot be reconciled is not softened, it is
  flagged.
- **Read-back before terminal claims.** Before asserting that something completed,
  the platform re-reads the authoritative state rather than trusting its own last
  observation.
- **Report fidelity is measured and gated.** Fidelity evals — claim precision and recall
  against material events — gate release, and a report-fidelity metric joins hook denial
  rate as a leading drift indicator in production.

> **Reports are presentation; attestation rests on records.**

Reports may render, summarize, and prioritize. They may not be the source of any claim.

## Consequences

A report can be trusted in the way an audit artifact needs to be trusted: every statement
in it traces to a record, and the ones that could not be verified are visible as gaps
rather than smoothed into prose. That is what makes the platform's output usable as
evidence rather than merely as a status update.

Fidelity as a *measured* property rather than an aspiration is the part that keeps this
true over time. Prompt changes, model changes, and template changes all degrade reporting
in ways nobody notices manually; the eval catches it, and the production metric catches
drift the eval missed.

The costs are real. Compiling from records is more engineering than prompting for a
summary, and it constrains what a report can say — if the record does not contain
something, the report cannot claim it, even when the model "knows" it. Read-back before
terminal claims adds latency and an extra call at exactly the moment users want the answer.

Building the fidelity eval corpus is genuine work, and it requires labeled material events
to score against. That corpus is also the thing most likely to be skipped under schedule
pressure, which would leave the decision nominally in force and practically unenforced.

This decision also sets the boundary that attestation scope decisions later depend on:
what a report can honestly claim is determined by what was recorded, which is why the two
integration paths evidence different things
([ADR-0032](0032-delegated-run-versus-local-loop.md)).
